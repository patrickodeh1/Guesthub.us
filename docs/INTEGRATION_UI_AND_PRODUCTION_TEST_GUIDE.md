# GuestHub Integration UI and Deployment Test Guide

This guide is the handoff checklist for validating the integration code in staging and then enabling providers in production. It separates application-code checks from provider onboarding, account authorization, certification, and live verification.

## Current status

- The integration implementation and automated test fixes are on `integrations/phase-0-pricelabs-safety`.
- The repository owner reports that the full automated test suite now passes.
- The code portion of this integration work is ready for UI/staging verification and handoff to the next development task.
- A passing test suite does **not** mean provider accounts, credentials, callback registration, OTA connections, payment flows, or provider certification have been verified live.
- Keep Channex on staging and keep PriceLabs IAPI disabled until the corresponding external prerequisites below are complete.
- Telnyx and Google are unchanged and are not part of this test plan.

## 1. Before testing

### 1.1 Deploy to a staging environment

1. Pull `integrations/phase-0-pricelabs-safety` into the staging release.
2. Back up the staging database.
3. Confirm the staging `.env` contains the intended provider credentials. Do not copy production secrets into staging unless the provider explicitly supports a safe test credential.
4. Confirm the application URL includes its deployed sub-path (currently `/welcome`). Callback and redirect URLs must be generated by Laravel routes, not manually assembled.
5. Confirm the queue worker and scheduler are running. Booking, calendar, reservation, and outbox updates use queued work.
6. Confirm the Laravel cache store is shared across app instances if the deployment has multiple servers; the PriceLabs partner-token rate limiter depends on shared cache for a global limit.

### 1.2 Review configuration

Check these settings without printing secret values:

| Provider | Configuration to confirm | Staging expectation |
|---|---|---|
| PriceLabs IAPI | `PRICELABS_INTEGRATION_NAME`, `PRICELABS_INTEGRATION_TOKEN`, `PRICELABS_IAPI_BASE_URL` | Leave credentials empty until PriceLabs issues development credentials. Base URL should be `https://api.pricelabs.co/v2/integration/api`. |
| Wheelhouse | `WHEELHOUSE_BASE_URL`, optional retained `WHEELHOUSE_WEBHOOK_SECRET` | Base URL `https://api.usewheelhouse.com/ss_api/v1`; each host supplies their own read-only RM API key. |
| Seam | `SEAM_API_KEY`, `SEAM_WEBHOOK_SECRET` | Use a Seam test workspace/key and test Yale/August accounts where available. |
| Channex | `CHANNEX_API_KEY`, `CHANNEX_BASE_URL`, `CHANNEX_DEFAULT_CURRENCY`, `CHANNEX_WEBHOOK_SECRET` | Keep `CHANNEX_BASE_URL=https://staging.channex.io/api/v1`. |
| Stripe Connect | `STRIPE_KEY`, `STRIPE_SECRET`, `STRIPE_CLIENT_ID`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONNECT_WEBHOOK_SECRET` | Use Stripe test mode and a Connect test account. |

Never put secrets in Git, this guide, screenshots, support tickets, or chat.

### 1.3 Run deployment checks

Run from the application release directory (adapt the container prefix to the deployment):

```bash
php artisan about
php artisan migrate:status
php artisan migrate --force
php artisan route:list --name=webhooks.pricelabs
php artisan route:list --name=webhooks.stripe.connect
php artisan route:list --name=admin.connect
php artisan route:list --name=properties.availability
php artisan channex:verify
php artisan integrations:report-shared-key-usage
php artisan view:clear
php artisan config:cache
```

Review the shared-key report before changing any affected property's pricing configuration. The report is read-only; it does not migrate or unlink properties.

Confirm that the queue worker is active and that scheduled commands are registered:

```bash
php artisan schedule:list
php artisan queue:work --once
```

Use the deployment's normal supervised queue worker in real operation; the one-shot command is only a smoke check.

## 2. UI test setup

Create or identify two separate host accounts, Host A and Host B. Give each host at least one property. Use distinct provider test accounts/credentials for the two hosts wherever the provider supports it.

Also prepare:
- An admin account.
- A manager account assigned only to Host A's property.
- A cleaner/housekeeper account assigned only to Host A's property.
- A guest booking on a test property for guest-payment checks.

For every provider, verify both the successful flow and the isolation boundary: Host A must not see, change, or use Host B's credentials, listings, devices, property IDs, channel connections, or Stripe account.

## 3. Provider UI tests

### 3.1 PriceLabs — legacy host key mode

1. Sign in as Host A and open a property’s Availability/pricing settings.
2. Select PriceLabs as the property's pricing provider.
3. Enter Host A's own PriceLabs API key and use the UI's validation/save action.
4. Confirm the key is masked after saving; the full key must not be rendered back into the page.
5. Confirm the property's PriceLabs listing selection/status is scoped to Host A.
6. Repeat for Host B with a different key.
7. Sign in as Host A and verify Host B's listing/credentials cannot be selected or displayed.
8. Switch a test property from PriceLabs to Wheelhouse and confirm the old provider linkage is cleared as intended.
9. Review `php artisan integrations:report-shared-key-usage`; resolve each reported legacy property deliberately before production cutover.

Expected: no shared/global PriceLabs API-key fallback is used. A host without their own key cannot access another host's PriceLabs account.

### 3.2 PriceLabs — IAPI/PMS mode (only after development credentials are issued)

Do not run this section with blank or guessed credentials.

1. Configure the development `PRICELABS_INTEGRATION_NAME` and `PRICELABS_INTEGRATION_TOKEN` in the staging secret store.
2. Set `PRICELABS_IAPI_BASE_URL=https://api.pricelabs.co/v2/integration/api`.
3. Use the development account email during partner onboarding and the host's registered PriceLabs account email in the host UI.
4. As Host A, open the property's Availability settings, select PMS/IAPI mode, enter the registered PriceLabs account email, and use the listing-registration action.
5. Confirm the listing is registered once and the UI reports listing/calendar status and timestamps. Confirm the initial calendar covers at least 730 days.
6. Confirm the reservation backfill and calendar push complete in the queue/logs. Ensure the listing uses the documented single-unit/USD mapping unless the integration contract has been changed.
7. Confirm the callback URLs registered with PriceLabs are the actual staging URLs generated by the app, including the deployed sub-path.
8. Have PriceLabs perform its callback URL verification probe. Each `{"verify":true}` probe must receive HTTP 200.
9. Send provider-signed test callbacks through the PriceLabs development integration. Confirm valid signatures are accepted and modified/missing signatures are rejected.
10. Confirm incoming rates update the intended availability ledger and do not echo back to PriceLabs as a new outbound update.
11. Change a booking and a host-entered block; confirm reservation/calendar deltas are queued. Reopen a previously synchronized manual block and confirm the matching cancellation is sent.
12. Repeat with Host B and verify listing IDs and callbacks cannot cross host boundaries.

Expected: the code is built, but IAPI remains inactive until the provider has issued credentials and the development callback/pilot checks pass. Only minimum-stay settings are currently enabled; do not imply other PriceLabs settings are supported.

### 3.3 Wheelhouse

1. Sign in as Host A and open the property's Availability/pricing settings.
2. Choose Wheelhouse and paste a read-only RM API key created inside Host A's own Wheelhouse account.
3. Save/validate the key. Confirm an invalid or revoked key produces a clear error and is not stored as a usable connection.
4. Confirm the listing picker shows only Host A's listings, with the listing title and channel.
5. Select the correct listing and save.
6. Trigger the normal sync path or wait for the scheduled `wheelhouse:sync` run. Confirm recommendation dates, prices, and minimum stays appear in the availability ledger and flow into the Channex outbox.
7. Repeat for Host B with a different key and listing.
8. Sign back in as Host A and verify Host B's listing and recommendations are not visible.
9. Confirm the UI never displays the complete API key.

Expected: Wheelhouse is read-only from GuestHub's side. GuestHub does not create Wheelhouse accounts or push calendars/reservations to Wheelhouse. The retained webhook/signing-secret decision is still an owner decision; do not remove it as part of this test.

### 3.4 Seam — Yale and August

1. Confirm the staging Seam workspace key and webhook secret are configured.
2. Sign in as Host A and open the lock-account connection area.
3. Start the Seam Connect Webview and complete the Yale or August sign-in using a test account.
4. Confirm the return flow associates the connected account with Host A.
5. Confirm the device picker lists only devices from Host A's connected account, with useful labels/provider/battery information rather than exposing raw device IDs.
6. Assign one device to Host A's test property and save.
7. Attempt to assign a device connected by Host B to Host A's property; the server must reject it.
8. Trigger the supported connected-account reauthorization event and confirm the UI shows a reconnect-needed state without deleting the assigned lock record.
9. Restore the connection and confirm the account returns to connected.
10. Confirm existing guest unlock/lock and cleaner session door flows still work with the test lock.

Expected: only Yale and August are enabled by this implementation. A real device operation must be tested with an approved test lock before production use.

### 3.5 Channex — staging property and channel connection

1. Confirm `CHANNEX_BASE_URL=https://staging.channex.io/api/v1` and a staging API key.
2. Run `php artisan channex:verify`; confirm it reports staging and validates the key without printing it.
3. Sign in as Host A and open a property’s channel/Channex settings.
4. Use the create-in-Channex action. Confirm property, room type, and rate plan are created and their IDs are saved to that GuestHub property.
5. Retry the create action. Confirm it resumes/reuses saved IDs rather than creating duplicates.
6. Open the channel-management iFrame for Host A's property and connect a staging OTA/channel account.
7. Sign in as Host B and attempt to open Host A's iFrame/property connection. Confirm access is denied.
8. Confirm availability/restriction outbox pushes still work.
9. Send or replay a staging webhook for Host A's Channex property. Confirm it updates only Host A's matching GuestHub property and booking data.
10. Confirm the Channex environment indicator is visible to admins and correctly identifies staging.

Expected: Channex remains on staging. Production access and certification are separate gates; do not change the base URL to production merely because staging tests pass.

### 3.6 Stripe Connect — test mode

1. Configure the Stripe Connect OAuth client ID, redirect URL, platform webhook, and Connect webhook in Stripe test mode.
2. Ensure the OAuth redirect URI exactly matches the app-generated `admin.connect.return` URL, including `/welcome` if deployed under that sub-path.
3. Ensure the Connect webhook endpoint uses the app-generated `webhooks.stripe.connect` URL and subscribes to connected-account events including `account.updated` and `account.application.deauthorized`.
4. Store the Connect webhook signing secret as `STRIPE_CONNECT_WEBHOOK_SECRET`.
5. Sign in as Host A and connect a Stripe Standard test account through OAuth.
6. Confirm the UI shows connection/capability state and does not expose tokens or secrets.
7. Repeat with Host B and a different connected test account. Confirm each host sees only their own account state.
8. Enable card payments for a test property only after the connected account reports charges enabled.
9. Create a test guest deposit and an itemized charge. In Stripe test mode, verify the PaymentIntents are created on the property's connected account, not the GuestHub platform account.
10. Test with a host that has no connected account and with a connected account whose charges are disabled. Guest card payment must be blocked with a clear message.
11. Deliver an `account.application.deauthorized` event for Host A. Confirm only Host A's connected-account fields are cleared and Host B remains connected.
12. Reconnect Host A and repeat a small test payment.

Expected: no host payment is created on the platform account by fallback. Do not use real cards or live money during staging.

## 4. Cross-provider regression checks

- Confirm each property's pricing provider is mutually exclusive and switching providers clears stale linkage fields.
- Confirm host A cannot view or use host B's provider credentials or linked records.
- Confirm queue failures surface a useful provider error and do not silently mark a sync successful.
- Confirm secrets are masked in every UI and absent from logs.
- Confirm app URLs and callbacks work with the deployed `/welcome` prefix.
- Confirm existing booking, guest checkout, cleaner session, door-access, and channel outbox flows remain functional.
- Confirm Telnyx and Google behavior is unchanged.

## 5. Production readiness gates

Do not treat staging success as production approval. Complete these gates in order.

### Gate A — application release

- [ ] Owner has pulled the integration branch and confirmed the full PHPUnit suite passes.
- [ ] Production database backup and rollback plan are ready.
- [ ] Production migrations have been reviewed and applied in the planned release window.
- [ ] Queue workers, scheduler, shared cache, logs, and monitoring are operational.
- [ ] `/welcome` route generation and webhook reachability are confirmed from outside the production network.
- [ ] Host-isolation checks have been completed with two separate test hosts.

### Gate B — provider onboarding

- [ ] **PriceLabs:** PriceLabs has issued GuestHub's integration name/token; development callback verification and pilot have passed; certification is complete before production activation.
- [ ] **Wheelhouse:** each production host supplies their own read-only RM API key and selects their own listing.
- [ ] **Seam:** production workspace credentials/webhook are configured and Yale/August real-device connection and assignment have been tested.
- [ ] **Channex:** production account access and certification are complete; production API key and production base URL are explicitly approved.
- [ ] **Stripe:** live Connect OAuth and Connect webhook settings are configured; a controlled live connected-account payment has been verified before accepting guest payments.

### Gate C — controlled rollout

1. Enable one approved test host/property first.
2. Verify provider status, logs, queue jobs, callbacks, and downstream ledger/outbox updates.
3. Verify a second host cannot access the first host's records.
4. Expand to a small pilot group and monitor errors/rate limits.
5. Enable wider production use only after the pilot is stable and the relevant provider has approved the integration.

## 7. Useful operational commands

```bash
# Verify Channex configuration without printing its API key
php artisan channex:verify

# Read-only report of PriceLabs properties that may have relied on the removed shared key
php artisan integrations:report-shared-key-usage

# Register the PriceLabs IAPI callbacks after PriceLabs issues partner credentials
php artisan pricelabs:register-integration

# Inspect scheduled jobs and queue status
php artisan schedule:list
php artisan queue:failed
```

Do not run the PriceLabs registration command until the partner integration credentials and correct staging callback host are configured. Do not switch Channex to production until Channex grants production access and certification is complete.
